# 32 — 凭证管理前后端契约修复（AK/SK 新增 422）

> 日期：2026-09-21
> 性质：缺陷修复（前端契约脱节导致所有凭证新增/编辑必然 422）

---

## 问题现象

资产管理 → 凭证管理，新增任意类型凭证（含云厂商 AK/SK）均失败：

```
INFO: 127.0.0.1:28814 - "POST /api/credentials HTTP/1.1" 422 Unprocessable Entity
```

复现报文（前端实际发送）：

```json
{ "name": "测试AK", "type": "access_key", "access_key": "AK123", "secret_key": "SK456" }
```

后端 422 明细：`body.content: Field required`、`body.expires_at: Field required`。

---

## 根因：前端与后端契约完全脱节

后端 `CredentialCreate` 只接受**单个加密 content 字段**（`backend/app/api/credentials.py`）：

| 后端字段 | 说明 |
|---|---|
| `name` | 凭证名称 |
| `type` | 类型字符串 |
| `content` | 必填，密文载体，入库前 `encrypt_secret` |
| `expires_at` | 必填，`YYYY-MM-DD`，用于计算 active/expiring/expired |
| `allowed_roles` | 可选，授权权限组；空 = 全部权限组可用 |
| `scope` | 可选，适用范围 |

而前端 `CredentialCreate` 类型长期停留在另一套字段：`username`/`password`/`private_key`/`passphrase`/`token`/`access_key`/`secret_key`/`description`——**后端一个都不认**。同时前端 `CredentialResponse` 里的 `username`、`updated_at` 后端也从不返回。

也就是说：凭证页的新增/编辑功能从后端那次改造之后就一直不可用，只是此前未被发现。

### content 的格式约定（由既有消费方反推确定，非新设计）

- `AccessKey` → JSON：`{"access_key":"...","secret_key":"..."}`
  （`certificates.py: parse_access_key_content` 解析；`_build_export_payload` 导出为 JSON）
- `SSH Key` → PEM 私钥原文（`assets.py` 取回后直接做 `pkey`）
- `Password` / `Token` → 明文原样（`assets.py` 取回后直接做 `password`）

库里既有的 3 条凭证（`aliyun`/`aliyun-hk`/`local-ssh`）解密后正是这两种格式，确认约定成立。

### 类型取值必须与后端判断对齐

`_build_export_payload` 与 `is_long_lived_key_type` 按字符串判断：

- `"AccessKey"` → 命中 `accesskey`（导出 JSON、按长期有效算状态）
- `"SSH Key"` → 命中 `ssh key`（导出 .pem、按长期有效）
- `Password` / `Token` → 走明文导出与常规过期逻辑

旧前端的 `access_key`/`ssh_key`（带下划线）两个判断都命中不了，会把 AK/SK 导出成 .txt、SSH 密钥导成 .txt。故统一改为后端语义的取值。

---

## 修复内容

### 1. `frontend/src/types/api.ts`

- `CredentialCreate` 重写为 `{ name, type, content, expires_at, allowed_roles?, scope? }`
- 新增 `CredentialUpdate`（`content?` + `replace_content`，对应后端"留空即不改动密文"语义）
- `CredentialResponse` 去掉 `username`/`description`/`updated_at`，补 `created_at`
- `CredentialType` 改为 `'Password' | 'SSH Key' | 'Token' | 'AccessKey'`

### 2. `frontend/src/pages/assets/credentials/index.tsx`

- 新增 `buildContent(type, values)`：按类型把表单字段组装成单个 content 字符串（AK/SK 走 `JSON.stringify`）
- 抽屉表单补齐后端必填项：**过期时间**（DatePicker，AK/SK 与密钥默认一年）、**适用范围**、**授权权限组**（多选，数据来自 `GET /credentials/access-options`，空 = 全部）
- 编辑态：密文字段留空即不改动，`replace_content` 仅在填写时为 true
- 表格列由"用户名/更新时间"改为**适用范围 / 授权权限组 / 创建时间 / 过期时间 / 状态**；SSH 密钥的 .pem 下载按钮判断同步改为 `type === 'SSH Key'`
- 合规导出 CSV 与加密备份包的字段同步对齐
- 新增 `credentialsApi.accessOptions`

### 3. `frontend/src/pages/assets/hosts/index.tsx`

主机页"快速新增 SSH 凭证"弹窗是同一 bug 的第二个入口，`handleCredSave` 改为组装 `content` + 默认一年 `expires_at`；用户名输入框降级为纯提示（登录用户以主机表单的 ssh_user 为准，后端凭证模型无用户名字段）。

### 4. `frontend/src/hooks/useCrudResource.ts`

新增第三个泛型 `TUpdate = TCreate`，让新增与编辑可以使用不同 payload 类型（凭证的 Create 必填 content、Update 可选 content）。泛型**追加在末尾**，不影响既有 `<TCreate, TId>` 调用方。

### 5. 顺带修复：应用配置中心的凭证下拉

`applicationsApi.getCredentialRefs()` 原请求 `GET /api/credentials/refs`——**后端没有这个路由**（实测 405，被 `PUT /{cred_id}` 捕获），且前端类型字段名 `credential_id`/`credential_type` 与后端返回的 `cred_id`/`type` 也不一致。改为后端真实存在的 `GET /api/applications/config-credential-options`，并修正字段名。

## 遗留与建议

1. **后端未做兼容层**：本次按"后端是唯一事实来源"修复前端。若担心还有别的旧前端/脚本在发旧字段，可在 `CredentialCreate` 加 `model_validator` 把 `access_key`/`secret_key` 等旧字段折叠进 content——目前未做。
2. **`/api/credentials/refs` 不存在**：已把前端调用切到正确路由，但建议后端要么补一个 `GET /credentials/refs` 兼容路由，要么在文档中明确废弃，避免第三方再踩。
3. **凭证无"用户名"概念**：后端 `credentials` 表没有用户名列，SSH 登录用户由主机的 `ssh_user` 决定。若产品上确需"凭证自带用户名"，需要加列 + Alembic 迁移（当前库有历史双 head，需先 merge）。
