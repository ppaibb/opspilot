# 33 — 账单同步字段映射修复（云账号加了但费用不显示）

> 日期：2026-09-21
> 性质：缺陷修复（阿里云 SDK 属性名大小写不匹配，同步"成功"但落库全为 0/空）

---

## 问题现象

费用管理 → 云账号绑定 AK/SK、点同步，接口返回成功、同步记录 `status=success`、
`rows_synced=31/33`，但费用总览、账单明细、各维度聚合**全部显示 0 或空白**，
"像没生效一样"。

数据库侧表现（`cloud_bills` 表）：

| 字段 | 实际值 |
|---|---|
| `pretax_amount` | 全表 0.0 |
| `payment_amount` | 全表 0.0 |
| `product_name` | 全空 |
| `instance_id` | 全空 |
| `region` / `billing_item_name` | 全空 |

---

## 根因：`getattr` 用了 PascalCase，SDK 模型属性是 snake_case

阿里云 BSS OpenAPI 的 `DescribeInstanceBill` 返回的 item，其
**Python SDK 模型属性名是 snake_case**（`product_name`、`pretax_amount`），
而 **`to_map()` 序列化出来的 JSON 键才是 PascalCase**（`ProductName`、`PretaxAmount`）。

`backend/app/services/bill_sync.py` 早期按 JSON 键名去 `getattr`：

```python
product_name=_s(item, "ProductName")      # → None → ""
pretax_amount=_f(item, "PretaxAmount")    # → 0.0
```

`getattr` 对不存在的属性静默返回 `None`（`_s`/`_f` 都有默认值兜底），
既不报错也不抛异常——所以同步流程一路"成功"，只是解析出来的每一行都是空壳。
**这是最隐蔽的一类故障：失败发生在取值环节，而不是业务流程环节。**

### 实测确认（用账号 1 的真实 AK/SK 调 BSS 接口）

```
getattr(item, "ProductName")   → <MISSING>
getattr(item, "product_name")  → '块存储'
getattr(item, "PretaxAmount")  → <MISSING>
getattr(item, "pretax_amount") → 1.765632
```

`item.to_map()` 的键：`AfterDiscountAmount`、`BillAccountID`、`BillingDate`、
`BillingItem`、`CostUnit`、`Currency`、`DeductedByCoupons`、`InstanceID`、
`ItemName`、`NickName`、`PipCode`、`PretaxAmount`、`ProductCode`、
`ProductDetail`、`ProductName`、`Region`、`SubscriptionType`、`Tag`、`Zone`…（共 41 个）

### 顺带查明的接口事实

| 前端/旧代码假设 | 接口真实情况 |
|---|---|
| `BillingItemName` 是计费项中文名 | **不存在**，中文名在 `item_name`（如「后付费账单」「续费」） |
| `ResourceName` 是实例名 | **不存在**，最接近的是 `nick_name`（实例备注名） |
| `Tags` 是对象数组 | **不存在**，只有 `tag`，且是字符串：`key:acs:ros:stackId value:4fa9...;key:env value:prod` |
| `PaymentAmount` / `CashAmount` | **不存在**，实付金额需另调 `QueryBillOverview`；本接口只给 `PretaxAmount` / `PretaxGrossAmount` / `AfterDiscountAmount` |
| `BillingItem` 是计费项编码 | 存在但常为空串，编码实际在 `pip_code` |
| 外层 `AccountID` / `NextToken` | 实际是 `account_id` / `next_token`（同样 snake_case） |

---

## 修复内容

### `backend/app/services/bill_sync.py`

1. **`_row_from_item` 全字段改 snake_case 取值**，并补两处回落：
   - `billing_item_code`：`billing_item_code` 为空时回落 `pip_code`
   - `resource_name`：取 `nick_name`
   - `billing_item_name`：取 `item_name`
2. **新增 `_parse_bill_tags(raw)`**：把 `key:xxx value:yyy;...` 字符串解析成
   `[{"key":..,"value":..}]` JSON。`key:` 取到下一个空格为止，`value:` 取到段尾，
   值里带空格（中文备注）不会被切断。
3. **`_dedup_key` 同步改 snake_case**：原实现用 PascalCase 取实例 ID/产品编码，
   去重基基本是空串，等于"只按 seq 去重"——同一天重同步时行与行的对应关系会漂移。
4. **`fetch_daily_bills`**：`AccountID/AccountName` → `account_id/account_name`；
   去掉 `NextToken` 回落（不存在，留着只会误导）。
5. `_row_from_item` 上方加注释说明 `payment_amount`/`cash_amount` 恒为 0 的原因，
   避免后人凭猜"修"成别的字段。

## 遗留与建议

1. **实付金额（`payment_amount`）恒为 0**：`DescribeInstanceBill` 不返回该字段。
  费用总览/账单/聚合全部以 `pretax_amount`（税前应付）为准，前端也未展示实付列，
  因此不影响本次问题。若产品上要区分"应付 vs 实付"，需另调
   `QueryBillOverview` 或 `DescribeInstanceBill` 的月度粒度，并新增落库字段。
2. **同步"成功"但数据为空仍无法自检**：`rows_synced` 只统计行数，不校验金额。
  建议后续在 `sync_account_cycle` 里加一条兜底：当日有行但 `pretax_amount` 全为 0 时，
  记一条 warning 到 `BillSyncRun.error_message`（不影响 status），让这类静默失败可见。
3. **`monthly_trend` 里 2026-03 ~ 2026-08 均为 0.0**：账号是近期才创建的，
  历史月份无数据，属预期，不是缺陷。
