## ✅ 任务 2：配置版本对比与回滚

### 实施时间
2026-08-20 上午（2 小时完成）

### 已实现功能

#### 后端接口

**1. 配置对比接口** `GET /api/applications/{app_id}/configs/{config_id}/compare`
- 参数：`target_revision_id`（目标历史版本 ID）
- 返回：当前版本、目标版本的完整信息 + diff 文本
- 使用 Python `difflib.unified_diff` 生成统一差异格式
- 支持对比任意两个版本

**2. 配置回滚接口** `POST /api/applications/{app_id}/configs/{config_id}/rollback`
- 参数：`{ target_revision_id }`
- 操作流程：
  1. 读取目标版本内容
  2. 更新当前配置为目标版本的值
  3. 创建新的版本记录（`change_type="rollback"`）
  4. 记录备注："回滚到版本 X"
- 权限：复用 `action.apps.config.manage`
- 安全：只能回滚当前应用的配置，跨应用隔离

#### 前端实现

**1. ConfigDiffViewer 组件** (`src/components/ConfigDiffViewer.tsx`)
- 抽屉宽度：1200px（适合左右对比）
- 顶部元信息：
  - 当前版本：版本号、更新时间、操作人、值类型、凭证引用
  - 目标版本：版本号、更新时间、操作人、值类型、凭证引用
- 双 Tab 视图切换：
  - **统一差异视图**：上下对比，适合查看少量差异
  - **左右对比视图**：并排显示，适合查看大量变更
- 使用 `react-diff-viewer-continued` 库
- 支持词级对比（`DiffMethod.WORDS`）
- 右上角"回滚到此版本"按钮
- 集成 `useRiskConfirm` 高危操作确认
- 无差异时禁用回滚按钮并提示

**2. 配置管理页面** (`src/pages/apps/config/index.tsx`)
- 路由：`/apps/:appId/config`
- 配置列表表格（7 列）：
  - 配置键、环境、值类型、配置值、备注、更新时间、操作
- 搜索框：支持按键、值、备注搜索
- 每行"历史"按钮打开历史版本抽屉
- 历史版本列表：
  - 显示版本 ID、变更类型 Tag（create/update/rollback）、时间、操作人
  - 每行"对比"和"回滚"按钮
- 点击"对比"打开 ConfigDiffViewer 抽屉
- 点击"回滚"直接触发回滚（带确认）

**3. 路由配置**
- 添加 `/apps/:appId/config` 路由
- 导入 `AppConfigPage` 组件

**4. API 类型扩展**
- `applicationsApi.list` 参数增加 `group_id?: number`
- 支持应用分组过滤

### 技术细节

**依赖包**：
- `react-diff-viewer-continued@4.4.0`（MIT 协议，React 18+ 兼容）

**后端数据流**：
```
对比流程：
1. 查询当前配置 + 目标历史版本
2. 使用 difflib.unified_diff 生成差异
3. 返回 { current, target, diff_text, has_changes }

回滚流程：
1. 验证目标版本存在
2. 提取目标版本的 value、value_type、credential_ref
3. 更新当前配置
4. _add_config_revision 记录新版本
5. 返回更新后的配置对象
```

**前端数据流**：
```
1. 配置列表 → useQuery(['application-configs', appId])
2. 点击"历史" → useQuery(['config-revisions', appId, configId])
3. 点击"对比" → useQuery(['config-compare', appId, configId, revisionId])
4. 点击"回滚" → useRiskConfirm → useMutation rollback
5. 成功 → invalidateQueries → 关闭抽屉
```

## 任务 1：部署异步化 🔥

### 背景
当前 Compose 项目部署是同步操作，大型项目（如 Harbor）部署可能需要 3-5 分钟（拉取镜像、启动多个容器），用户只能等待，体验差，且容易误以为系统卡死。

### 目标
将部署改为后台异步任务，用户提交后立即返回，可以关闭页面或继续其他操作，部署完成后通过站内通知提醒。

### 技术方案

#### 后端改动

**1. 引入后台任务框架**
- 使用 Python `threading` 或 `asyncio.create_task` 启动后台任务
- 任务状态存储到新表 `application_deployment_tasks`：
  ```python
  class ApplicationDeploymentTask(Base):
      __tablename__ = "application_deployment_tasks"
      
      id = Column(Integer, primary_key=True)
      task_id = Column(String(50), unique=True, index=True)  # UUID
      app_id = Column(String(50), index=True)
      task_type = Column(String(30))  # compose_deploy / compose_update
      status = Column(String(30))  # pending / running / success / failed
      progress = Column(Integer, default=0)  # 0-100
      current_step = Column(String(100))  # 当前步骤描述
      result_summary = Column(String(500))  # 成功/失败摘要
      error_detail = Column(Text)  # 详细错误信息
      created_by = Column(String(80))
      created_at = Column(DateTime)
      updated_at = Column(DateTime)
  ```

**2. 部署接口改造**
- `POST /api/applications/{app_id}/components` 增加 `async_mode` 参数（默认 `false` 保持兼容）
- `async_mode=true` 时：
  - 立即返回 `{ task_id, status: "pending" }`
  - 启动后台线程执行部署
  - 每个步骤更新任务状态：
    ```python
    # 预检阶段
    update_task(task_id, status="running", progress=10, current_step="预检环境")
    # 写入配置
    update_task(task_id, status="running", progress=30, current_step="写入配置文件")
    # 拉取镜像
    update_task(task_id, status="running", progress=50, current_step="拉取镜像")
    # 启动容器
    update_task(task_id, status="running", progress=80, current_step="启动容器")
    # 验证状态
    update_task(task_id, status="running", progress=95, current_step="验证运行状态")
    # 完成
    update_task(task_id, status="success", progress=100, result_summary="...")
    ```

**3. 任务查询接口**
- `GET /api/applications/deployment-tasks/{task_id}`
  - 返回：`{ task_id, status, progress, current_step, result_summary, error_detail, created_at, updated_at }`
- `GET /api/applications/{app_id}/deployment-tasks`
  - 返回该应用的部署任务列表（最近 10 条）

**4. SSE 推送（可选）**
- 复用现有站内通知 SSE 连接
- 任务状态变更时推送到前端：`{ type: "deployment_progress", task_id, status, progress }`

**5. 完成后通知**
- 部署成功/失败后调用 `create_notification` 写入站内通知
- 通知内容：应用名称、部署结果、登记组件数/失败原因

#### 前端改动

**1. 部署表单**
- "开始部署"按钮改为提交异步任务
- 提交后跳转到"部署进度"页面或在当前页显示进度卡片

**2. 进度展示组件**

- 显示当前步骤文字

- 状态图标：
  - `pending`: <ClockCircleOutlined /> 等待中
  - `running`: <LoadingOutlined /> 部署中
  - `success`: <CheckCircleOutlined style={{ color: '#52c41a' }} /> 部署成功

### 技术方案

#### 后端改动

**1. 配置对比接口**
- `GET /api/applications/{app_id}/configs/{config_id}/compare?target_revision_id={id}`

    ```json
    {
      "current": { "revision_id": 123, "version": "v5", "content": "...", "updated_at": "..." },
    ```

## 风险与应对

### 风险 1：部署异步化的并发控制
**问题**：多个用户同时部署同一应用的不同组件可能冲突  
**应对**：后端检查是否已有进行中的部署任务，如有则拒绝新任务

### 风险 2：配置回滚的数据一致性
**问题**：回滚配置后，运行实例未重启可能导致配置不生效  
**应对**：回滚后提示用户"配置已更新，需要重启应用生效"

### 风险 3：实例详情抽屉的数据加载
**问题**：打开抽屉时需要额外请求详情接口，可能有延迟  
**应对**：抽屉打开时显示 Skeleton 占位，异步加载完成后填充内容
