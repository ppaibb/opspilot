# IM 智能运维闭环（塔斯汀模式：告警 → AI 根因 → 人工反馈 → 经验沉淀）

> 创建日期：2026-09-19  
> 状态：P0 完成（真 LLM 分析 + 根因三元组沉淀 + AI 准确率统计 + IM 卡片处理链接）

## 📊 背景

对标塔斯汀（万店连锁）基于 CMS 2.0 + STAROps 的智能运维闭环实践。核心思想：
**"告警之后才是运维效率的分水岭"**——把 AI 输出从"一次性结论"升级为
**可反馈、可沉淀的数据**，让平台持续学习。

OpsPilot 的现状盘点（改造前）：
- ✅ 已有：告警中心（活跃/历史/静默/确认）、通知渠道（飞书/企微/钉钉 Webhook）、
  告警防抖、AI LLM 基础设施（模型配置 + 三家 provider）
- ❌ 缺失：`/analyze` 是 **Mock**（sleep 1.5s 返回硬编码文案）、无根因沉淀、
  无 AI 反馈闭环、IM 卡片无处理入口

## 一、本次改造（P0 范围）

### 1. Mock → 真 LLM 根因分析

`POST /api/monitoring/alerts/analyze` 重写（`services/alert_root_cause.py`）：
- 复用平台 LLM 运行时配置（Gemini / OpenAI 兼容 / Claude），严格 JSON 输出
  （root_cause / impact / suggestions），markdown 包裹容忍解析
- **历史根因注入（核心机制）**：分析时自动检索同类告警（同 alert_name）的
  人工根因（最多 5 条）作为 few-shot 经验——"AI 越用越贴业务"的落地
- 降级策略：LLM 未配置/失败时返回 `mode=fallback` 的结构化提示（含历史根因参考），
  **绝不返回编造内容**（对比旧 Mock 的虚构"400% 飙升"）

### 2. 根因反馈三元组（`alert_root_causes` 表）

一条记录 = 一次告警的完整处置沉淀：
- **上下文**：fingerprint / alert_name / service / instance / severity / 标签快照
- **AI 侧**：诊断 JSON + 所用模型（分析即落 pending 记录）
- **人工侧**：真实根因（"真正发生了什么"）+ 处理方式 + **AI 评价**
  （accurate / partial / inaccurate）

API：`GET /root-causes?alert_name=`（根因库检索）、
`POST /root-causes/{id}/feedback`（补齐人工侧）、`GET /root-causes/stats`（准确率统计）。

### 3. AI 准确率统计（可量化治理）

- 加权准确率 = (accurate + 0.5×partial) / 已评价数
- 整体指标 + 按告警名 Top 20 明细（样本数/准确率/分布）

### 4. IM 卡片处理入口

通知模板新增 `{{console_url}}` 变量（`CONSOLE_URL` 环境变量可配，默认前端告警中心地址）——
飞书/企微/钉钉卡片上放"处理入口"链接，把人从 IM 带回平台完成认领/分析/闭环
（链接型交互，P0 不依赖公网回调）。

## 二、前端

### 告警中心（alerts 页）

- 操作列新增**「根因」**按钮 → 根因分析抽屉（`AlertRcaDrawer`）：
  1. 「开始 AI 分析」：真 LLM 诊断（标注是否降级/引用了几条历史根因）
  2. 人工反馈表单：真实根因 + 处理方式 + AI 评价（三档）→ 沉淀
  3. 同屏展示**该类告警历史根因**（含 AI 评价 Tag、实例、时间、处理人）
- 统计卡下方新增**「根因库 · AI 准确率」**入口 → 根因库抽屉（`RootCauseLibrary`）：
  综合准确率/已评价样本统计卡 + 按告警名排行 + 根因记录流（按告警名检索）
