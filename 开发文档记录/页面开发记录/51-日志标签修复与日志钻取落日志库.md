## 二、日志标签修复：四个下拉从「只有 container / 三个空」到全部有值

### 现象与根因

日志页的 主机/服务/任务/级别 四个下拉各自向后端 `/api/monitoring/logs/fields`
查字段取值。235 实测 VLogs 里容器日志只有两个标签：

```
{instance="192.168.3.235", job="container"}     ← 没了 host，且从未有过 service/level
```

- 「任务」下拉里那个 `container` 其实是 `job` 标签的唯一**值**（所有容器日志共用），
  没有区分度；
- 「主机」空：HOST_NAME 丢失（见下）；
- 「服务」「级别」空：采集配置从来没打这两个标签。

### 三处根因、三份配置、一次修齐

alloy 采集配置一共存在**三份**，全部同步修复：

| 份 | 位置 | 适用场景 |
|---|---|---|
| 1 | `deploy/offline/monitoring/config/alloy.alloy` | 一体机离线部署（235 模式） |
| 2 | `deploy/monitoring/config/alloy.alloy` | 监控栈单独部署 |
| 3 | `backend/app/services/collector_config.py` `render_alloy_config()` | agent 远程模块模式（99 模式），由后端下发 |

**根因 A（host 标签丢失）**：HOST_NAME 只靠 install.sh 运行时 shell 导出，任何一次
不带导出的手工 `docker compose up -d alloy` 都会把它丢成空串（235 实际踩过——50 号
演练中我只重建了 alloy）。修复：install.sh 把 `HOST_NAME` 持久化写进 `.env`
（已存在则跳过），后续任何 compose 调用都能取到。

**根因 B（service 标签缺失）**：三份配置的 docker 日志段都只打 job/host/instance。
补 `discovery.relabel` 把 `__meta_docker_container_name` 提升为 **`service` 标签**
（容器名，如 `opspilot-backend`），日志页「服务」下拉即列出全部容器。

**根因 C（level 标签缺失）**：补 `loki.process` 管线——`stage.template` 默认
`level=INFO` → `stage.regex` 从日志行提取大写级别词（DEBUG/INFO/WARN/ERROR/...）
覆盖 → `stage.labels` 落标签。「级别」下拉即出现 INFO/ERROR/...。

> 坑：`stage.template` 的属性名是 `template` 不是 `value`——写错 alloy 启动即崩
> （`unrecognized attribute name "value"`），且 bind-mount 的配置文件更新后
> `docker compose up -d` 不会重建容器，必须 `docker restart`。

### 修复后实测（235）

```
host    → testserver-305
service → opspilot-alloy / opspilot-backend / opspilot-frontend /
          opspilot-grafana / opspilot-victoriametrics / opspilot-db
job     → container
level   → INFO, ERROR
```

回归：`test_docker_logs_pipeline.py` 新增
`test_render_docker_labels_service_and_level` 钉死渲染器的 relabel/process 管线。

### 99 的说明（重要）

99 的 alloy 是 **agent 远程模块模式**：本地只有 16 行 bootstrap，真实采集配置由
`http://192.168.2.200:8001`（另一套 OpsPilot 部署）的
`/api/monitoring/collector/agent/module` 每 60 秒下发。所以 99 上手改本地文件无效——
后端渲染器（第 3 份）已修好，**等 2.200 那套 OpsPilot 升级后端即自动生效**。

## 三、日志钻取落 Grafana 日志库（不再查 VM）

### 原状

日志页「Grafana」按钮复用指标钻取组件：LogsQL 被当作 PromQL、指向指标数据源
`opspilot-vm`——查的根本不是日志库。

### 修复

1. **Grafana 装 VictoriaLogs 数据源插件**（`victoriametrics-logs-datasource` v0.32.0，
   来自 `VictoriaMetrics/victorialogs-datasource` releases）。
   两个坑：
   - 插件**不在 grafana.com 目录**，`GF_INSTALL_PLUGINS` 直接 404，只能手动装：
     下载 zip → 解压 → `docker cp` 进 `/var/lib/grafana/plugins/`（grafanadata 卷，
     跨重建有效）→ 重启。步骤已写进 `deploy/README.md` 第六节；
   - GitHub releases 大文件直连慢/断，用 gh-proxy 前缀一次拉全（本机与 235 直连均
     超时/截断）。
   compose 加 `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=victoriametrics-logs-datasource`。
2. **provisioning** 新增 `opspilot-victorialogs.yml`（两份部署包各一）：
   uid `opspilot-vlogs`、type `victoriametrics-logs-datasource`、
   url `http://victorialogs:9428`（compose 服务名，静态 URL，见 49 号的插值坑）。
3. **前端**：`GrafanaLink` 支持 `datasource` 参数——传了就按 Grafana 11 的
   `schemaVersion=1&panes={...}` 格式带指定数据源与 `queryType:"range"`；数据源常量
   抽到独立文件 `grafanaDatasources.ts`（`GRAFANA_DS_METRICS`/`GRAFANA_DS_LOGS`，
   组件文件不允许再导出常量，react-refresh 规则）。日志页传 `GRAFANA_DS_LOGS`，
   空查询也从 `""` 改为 `"*"`（LogsQL match-all，避免 Explore 空表达式报错）。

### 修复后实测（235，GUI 实证）

日志页填 `level:ERROR` 点「Grafana」→ 新标签打开
`/grafana/explore?schemaVersion=1&panes={"6nm":{"datasource":"opspilot-vlogs",...}}`，
Explore 左上是 **OpsPilot VictoriaLogs**，LogsQL 带入，返回真实 ERROR 日志，
级别快捷过滤（critical/error/...）与通用标签（host/instance/service）齐全，
**0 失败请求**。
