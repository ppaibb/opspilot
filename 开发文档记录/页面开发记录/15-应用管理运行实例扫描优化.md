# 应用管理运行实例扫描与批量清理

> 持续更新：2026-08-20

## 本轮产品结论

运行实例不是主机上所有进程的简单镜像，而是当前应用需要持续管理的业务运行单元。扫描结果必须经过"技术发现 → 业务过滤 → 去重确认 → 纳管"的过程，避免把数百个基础 Systemd 服务直接暴露给客户。

本轮将用户界面的主称呼从"运行实例"调整为"部署组件"。后端接口和历史数据继续保留 `ApplicationComponent` / runtime 兼容命名，避免破坏现有 API。

产品层级统一为：

```text
业务应用 → 部署 → 部署组件 → 运行方式
```

例如 Harbor 应用下可以有一个 Compose 部署，下面包含 `core`、`registry`、`portal` 等部署组件。

## Compose 项目从零部署

新增“整个 Compose 项目”部署闭环：

1. 在“添加部署组件”中选择“全新部署”和“Docker Compose 服务”。
2. 选择当前应用已绑定的目标主机，填写 Compose project、部署目录、文件名、Compose YAML 和可选 `.env`。
3. 必须先执行部署前检查；检查过程使用远程临时目录，不写目标部署目录、不拉镜像、不创建、停止或重启容器。
4. 预检检查 SSH、Docker daemon、Compose CLI、目录可写性，并执行 `compose config --services` 验证 YAML 和服务列表。
5. 预检通过后才允许开始部署。部署时写入配置、可选拉取镜像并执行项目级 `up -d`。
6. 部署成功后按 `com.docker.compose.project` 标签自动发现 services，并幂等登记为部署组件。

### 安全联调约定

- 不使用正在运行的 Harbor 作为首次部署测试目标。
- 测试 project 使用 `opspilot-compose-demo`，测试目录使用 `/opt/opspilot/test/demo`。
- 首次联调 Compose 文件只使用无状态测试镜像和独立端口，例如 `nginx:alpine` 的 `18080:80`。
- 自动化验证只检查命令生成、配置解析和路由加载，不连接生产主机执行部署。
- 人工点击“开始部署”前必须确认目标主机、project、目录和端口均不属于 Harbor。
- 全新部署会创建不存在的部署目录；如果目录已存在但非空，预检和正式部署都会拒绝，不覆盖任何文件。
- 如果目录已存在且为空，可以复用该目录；如果目录不存在，系统会创建它。
- 如果 Compose 文件或 `.env` 已存在于非空目录中，同样视为冲突并拒绝部署。

### 部署失败与启动失败处理

- 首次部署前检查目标 project 是否已有容器；如已存在则拒绝覆盖，避免误伤现有业务。
- 全新部署只允许写入不存在或空目录；因此不会覆盖既有 Compose / `.env` 文件，也不需要对已有业务配置做覆盖式备份。
- 拉取镜像、`up -d`、状态检查任一步失败时触发回滚：仅对本次新 project 执行 `down --remove-orphans`，随后恢复旧文件或删除本次新文件。
- `up -d` 成功后对比 Compose 配置服务数和实际运行服务数；未全部运行视为部署失败并回滚。
- 部署失败不写入部署组件数据库记录；后端返回退出码、远程错误和“已回滚”说明。
- 前端使用持久错误弹窗展示完整失败详情，不再用容易消失的短消息承载部署日志。
- 部署成功后才自动发现 service 并登记组件；发现失败会明确提示“项目已启动但登记失败”，不伪装为完整成功。

### 站内通知

- 全新部署成功或失败都会给当前操作人写入持久化站内通知，并通过 SSE 实时推送。
- 成功通知包含应用、运行方式、项目名和自动登记组件数量。
- 失败通知包含应用、运行方式和截断后的失败原因，并链接到 `/apps/{app_id}`。
- 预检不发送站内通知，因为它是同步只读检查，不属于后台任务终态。
- 本地后端启动日志中的 `127.0.0.1:8428` 连接拒绝属于监控告警引擎未启动，不影响 Compose 预检或部署接口；部署联调时可暂时忽略该类告警日志。

## API 变化

- `POST /api/applications/{id}/runtime-discovery` 新增可选参数 `include_system_services`，并返回 `filtered_count`。
- 扫描候选新增 `management_status` 和 `managed_component_id`。
- Docker Compose 候选新增 `project_name`，来源为容器的 `com.docker.compose.project` 标签。
- `ApplicationRuntimeActionResponse` 前端类型与后端统一为 `ok/stdout/stderr/code/target_count/duration_ms/notice`。
- Compose 控制命令在远程主机上通过受控 shell 函数选择 `docker compose` 或 `docker-compose`，不会把 Compose 参数交给 Docker 顶层命令。
- 新增 `POST /api/applications/{id}/compose/preflight`，该接口只做远程只读预检。
- Compose 项目部署仍复用 `POST /api/applications/{id}/components`，`create_mode=deploy` 成功后自动登记项目 services。
- `POST /api/applications/{id}/components` 保持原响应结构，重复身份直接返回已有实例，避免破坏现有前端调用。
- `POST /api/applications/{id}/components/batch-delete` 继续用于批量移除登记，单次最多 2000 条。
