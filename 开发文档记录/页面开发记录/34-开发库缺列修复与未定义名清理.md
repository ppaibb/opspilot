# 34-开发库缺列修复与未定义名清理

> 2026-09-21。本文件合并记录当天后端三次报障修复：开发库缺列导致 DB 管理页 500、
> PostgreSQL 驱动差异导致的 rowcount TypeError、以及一次 pyflakes 专项清理出来的 9 处未定义名。

## 一、开发库缺列：DB 管理页整页 500

### 现象

```
GET /api/db/query-logs?limit=30 HTTP/1.1" 500 Internal Server Error
psycopg.errors.UndefinedColumn: column db_instances.allowed_roles does not exist
```

前端提示"出了点问题，请刷新页面或联系管理员"。

### 根因

开发库的表结构由 `app/main.py` lifespan 里的 `Base.metadata.create_all(bind=engine)` 维护。
**`create_all` 只会创建缺失的表，不会给已存在的表添加新列**；而 Alembic 迁移按项目约定
只用来验证迁移文件本身，不往开发库上跑。

于是形成一个静默故障链：

1. 模型加一列 → 写一个 Alembic 迁移（用于将来生产库升级）
2. 开发库的表早就建好了，`create_all` 看到表存在就跳过，**不会执行那条 ALTER**
3. 老库一直缺这一列，日常毫无征兆
4. 直到某个查询把该列 SELECT 出来 → `UndefinedColumn` → 整页 500

实测把全部 47 张模型表与线上库结构逐一比对，共缺 **5 列**（不止用户报的那一列）：

| 表 | 缺失列 |
|---|---|
| `db_instances` | `allowed_roles` |
| `db_tickets` | `database`、`execute_after`、`backup_snapshot`、`rollback_statements` |

前 4 列来自 `20260920_db_enhance` 迁移，第 5 列来自更早的工单定时执行功能。
也就是说这类缺口已经攒了一阵，只是没被触发。

### 修复：把手写兜底泛化成 `ensure_model_columns()`

原来 `main.py` 里已经有一段针对 `audit_logs` 两列和 `assets` 两列的手写 `ALTER TABLE` 兜底
（说明前人早就踩过同一个坑，只是每次都只补自己那一处）。这次把它替换成按元数据反射的通用版本：

```python
def ensure_model_columns():
    """给已存在的表补齐模型新增的列（只增不删，逐列幂等）。"""
    from sqlalchemy import inspect as sa_inspect
    from sqlalchemy import text

    inspector = sa_inspect(engine)
    existing_tables = set(inspector.get_table_names())
    added: list[str] = []
    for table_name, table in Base.metadata.tables.items():
        if table_name not in existing_tables:
            continue
        present = {col["name"] for col in inspector.get_columns(table_name)}
        for column in table.columns:
            if column.name in present:
                continue
            try:
                type_sql = column.type.compile(dialect=engine.dialect)
                ddl = f"ALTER TABLE {table_name} ADD COLUMN {column.name} {type_sql}"
                # 没有服务端默认值时不加 NOT NULL，否则老数据行会违反约束
                if not column.nullable and column.server_default is not None:
                    ddl += " NOT NULL"
                with engine.begin() as conn:
                    conn.execute(text(ddl))
                added.append(f"{table_name}.{column.name}")
            except Exception as exc:  # noqa: BLE001
                print(f"[OpsPilot] 补列失败 {table_name}.{column.name}: {exc}")
    if added:
        print(f"[OpsPilot] 已补齐缺失列 {len(added)} 个：{', '.join(added)}")
```

启动时在 `create_all` 之后调用。几个刻意的设计：

- **逐列 try/except**：某一列补失败（比如类型无法编译）只告警，不阻断启动——补列是兜底，不该变成新的启动炸弹
- **NOT NULL 只在该列有服务端默认值时加**：老数据行已经存在，加一个无默认值的 NOT NULL 列会直接违反约束
- **只增不删**：库里多出来的列（可能是手工加的）不动

### 回归测试

`backend/test_audit_schema_contract.py` 从 1 例扩到 3 例：

1. `test_ensure_audit_columns_adds_risk_fields_for_legacy_sqlite` — 老库补 `audit_logs` 两列
2. `test_ensure_model_columns_is_idempotent` — 连跑两次不报错（幂等）
3. `test_ensure_model_columns_backfills_model_added_column` — **复现本 bug**：建表后 `ALTER TABLE db_instances DROP COLUMN allowed_roles`，跑补列，断言列回来了且能写能读

## 二、同页第二个缺陷：PostgreSQL 上的 rowcount TypeError

`/db/query-logs` 修好后，日志里暴露出最近一次自助查询其实也是失败的：

```
int() argument must be a string, a bytes-like object or a real number, not 'Cursor'
```

### 根因

`db_ops.execute_statements` 用 `int(cursor.execute(stmt) or 0)` 取影响行数。
**两个驱动的 `execute()` 返回类型不一样**：

| 驱动 | `cursor.execute()` 返回 |
|---|---|
| pymysql | `int`（影响行数） |
| psycopg3 | cursor 自身 |

所以这段代码在 MySQL 数据源上一直正常，在 PostgreSQL 数据源上每条语句（含 SELECT）执行完就抛 TypeError，被 except 捕获后记成 `ok=False`。**查询结果其实已经取到了**，只是统计行数那行炸掉，前端看到"执行失败"。

### 修复

改用 `cursor.rowcount`（两个驱动都支持，SELECT 时是结果集行数），并用 `max(0, ...)` 把 rowcount 为 -1（驱动无法确定行数）的情况兜底成 0：

```python
cursor.execute(stmt)
...
"rows_affected": max(0, int(cursor.rowcount or 0)),
```

### 回归测试

`test_db_ops_contract.py` 新增 `ExecuteRowCountContract` 3 例，用假 cursor 分别模拟两种约定（psycopg3 的 `execute()` 返回 self、pymysql 的返回 int），外加 -1 兜底。假 cursor 必须实现 `__enter__`/`__exit__`，因为执行器用的是 `with conn.cursor()`。

对真实 PG 数据源实测 CREATE/INSERT/UPDATE/DELETE/SELECT 的 `rows_affected` 分别为 0/3/1/1/2。

## 三、未定义名专项清理：`/db/instances/{id}/databases` 500

### 现象

```
GET /api/db/instances/1/databases HTTP/1.1" 500 Internal Server Error
NameError: name '_build_connection' is not defined
  File "app/api/database.py", line 730, in list_databases
```

### 根因

`db_ops.execute_statements` 拆分出去之后，`database.py` 直接用 `_build_connection` 却从未 import。

这类错误的特点是 **Python 编译期完全不报**——名字在函数体内，只有函数第一次被调用才解析。所以测试全绿、页面照样渲染，直到用户点开"数据库列表"。

### 不是个例

用 pyflakes 扫全 `app/`，同样的未定义名共 **9 处**：

| 文件 | 未定义名 | 触发场景 |
|---|---|---|
| `api/database.py:731/761` | `_build_connection` | 数据库列表 / 表列表（用户已报障） |
| `api/certificates.py:797/1015` | `AuditLog` | 证书自动续签失败/成功写审计——**会在 commit 前抛异常，把 cert 状态更新一起回滚** |
| `monitoring/services/proxy.py:127` | `base64` | 监控连接填了 Basic 认证时构造请求头 |
| `monitoring/services/log_targets.py:130` | `_normalize_vlogs_ingest_base` | 渲染远端 Vector/Alloy 的 sink 地址 |
| `monitoring/services/log_targets.py:240` | `_build_authorization_header` | 同上，sink 带认证时 |
| `monitoring/services/log_targets.py:375` | `User` | `_run_asset_ssh` 的类型注解（有 `from __future__ import annotations`，运行时侥幸不炸） |
| `monitoring/services/vmagent.py:247` | `save_monitoring_targets` | 启用/停用采集 target 时落库 |
| `monitoring/services/vmagent.py:252` | `HTTPException` | 同上，落库失败要抛 500 |

全部补上 import。`log_targets.py` 头部还有一段重复的 import 块（`json`/`re`/`Any` 导了两遍），一并合并。

### pyflakes 的盲区

`app/api/applications.py`、`application_routes/*`、`cluster_routes/*` 共 10 个文件用了
`from x import *`，pyflakes 对这类文件直接放弃分析，只打印一堆
"may be undefined, or defined from star imports"。

写了个临时脚本把这 10 个文件里的 `*` 展开成真实导出的名字再跑一遍 pyflakes，确认也干净。
脚本用完即删，不留在仓库里。

> 注：跑这个脚本必须用 `backend/.venv/Scripts/python.exe`。系统 python 没装 psycopg，
> 导致 `application_routes.shared` 等模块 import 失败、脚本静默跳过——那一次结果是假的。

### 验证

- `pytest -q` **365 passed**
- `pyflakes app/` 零 `undefined name`
- 真实 HTTP（uvicorn 8019 + admin 登录）：

| 接口 | 结果 |
|---|---|
| `GET /api/db/instances/1/databases` | **200** `{"databases":["opspilot","postgres"]}` |
| `GET /api/db/instances/1/tables?database=opspilot` | 200，41 张表带行数 |
| `GET /api/db/query-logs?limit=30` | 200 |
| `GET /api/db/instances` | 200，`allowed_roles:[]` 正常返回 |
| `POST /api/monitoring/targets/ins-c7514d03/check` | 走到 `save_monitoring_targets`，报"Alloy 配置文件不存在"（本机无 `/root/.nanobot/...` 部署目录，属环境条件非代码错误） |
| `POST /api/monitoring/log-targets/ins-c7514d03/check` | 走到 `_normalize_vlogs_ingest_base` + `_build_authorization_header`，返回真实 SSH 探测结果"vector not installed" |

证书审计路径单独跑通 `set_issue_failed`，`AuditLog` 正常落库。**验完已把该审计行、被改的证书状态和 `issue.log` 末行全部还原**——原始状态由日志里 `[2026-09-21 11:27:45] 续签超时兜底：状态已回刷为 expiring` 反推得出。

> 验证前要先确认目标函数会不会自己提交。

## 四、经验

这次 9 处未定义名集中在两种场景：

1. **把函数从 A 文件拆到 B 文件**，调用方忘了补 import（`_build_connection`、`_normalize_vlogs_ingest_base`、`_build_authorization_header`、`save_monitoring_targets`）
2. **新写一段代码忘了 import**（`AuditLog`、`base64`、`HTTPException`、`User`）

`pyflakes` 一条命令就能全查出来，比等用户点出 500 再回溯便宜得多。**建议并入提交前检查**：

```bash
cd backend && PYTHONPATH=<pyflakes目录> .venv/Scripts/python.exe -m pyflakes app/
```

同时要记住它对 `from x import *` 的文件会放弃分析，那部分需要额外手段覆盖。
