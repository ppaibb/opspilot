**权限配置发现（记录）**：内置「运维」角色含 `action.db.manage`——自助查询豁免授权校验，
即运维角色不经授权可查任何库。若非本意，应在「权限管理」页把运维的 `action.db.manage` 关掉
（本轮测试用 DBA+admin 组合绕开该豁免做了完整链路验证）。
**2026-10-05 追加**：权限目录里 `action.db.manage` 的描述原先只写"新增/编辑/删除数据源与连通测试"，
未提豁免副作用，管理员勾选时不知情。已把"持有该权限的角色做自助查询时豁免查询授权校验"写进描述
（`app/core/rbac.py` PERMISSION_CATALOG）。设计结论：能力授予模型本身合理（模板都是默认值、
可在权限管理页随意改），不必拆新权限键——把副作用说清楚即可。

## 二、修复的 2 个真实缺陷（备份回滚功能此前从未在 PG 上真实验证过）

**缺陷 1：回滚 SQL 方言错误——PG 实例生成的是 MySQL 语法。**
`build_rollback_inserts` 无条件用反引号包列名，PostgreSQL 里反引号是语法错误，
"导出回滚 SQL"功能在 PG 数据源上从上线起就是坏的。
修复：标识符引号按 `db_type` 选（PG 双引号 / MySQL 反引号），两个调用点传参。

**缺陷 2：UPDATE 工单的回滚是裸 INSERT，必然主键冲突。**
回滚语句形如 `INSERT INTO t (id, ...) VALUES (1, ...)`，而 UPDATE 后目标行还在，
回放必撞唯一约束。实测撞 `smoke_multiuser_t_pkey`。
修复：来源语句是 UPDATE 时，回滚生成 `UPDATE t SET 列=备份原值 WHERE <原子句>`（一条还原全部备份行）；
DELETE 场景保留 INSERT；无 WHERE/解析失败退回 INSERT 兜底。

**端到端证明**：`UPDATE smoke_multiuser_t ... WHERE id=1` 工单执行后，
导出回滚 SQL（`UPDATE smoke_multiuser_t SET "id" = 1, "note" = '...' WHERE id = 1;`），
在 PostgreSQL 上真实回放，数据还原到执行前值。

**契约测试**：`TestRollbackInsertsDialect` 3 例 + `TestRollbackUpdateForm` 3 例
（PG 双引号/MySQL 反引号/默认值；UPDATE 形式/DELETE 保持 INSERT/无 WHERE 兜底）。
