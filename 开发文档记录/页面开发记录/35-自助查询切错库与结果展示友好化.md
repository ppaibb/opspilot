## 一、起因：一条能跑通的 SQL 报"表不存在"

用户在自助查询里执行：

```sql
SELECT id, name, db_type FROM db_instances ORDER BY id
```

返回：

```json
{"ok": false, "error": "relation \"db_instances\" does not exist
LINE 1: SELECT id, name, db_type FROM db_instances ORDER BY id
                                      ^"}
```

**结论先说：SQL 没错，是连错了库。** 这条 SQL 连到 OpsPilot 自己的实例默认库 `opspilot`
能正常跑通（`db_instances` 是 OpsPilot 的业务表），而查询面板当时连的是 `postgres`
维护库——那里当然没有 OpsPilot 的表。

### 双向证明

不靠猜，直接把同一条 SQL 打到两个库上对比：

| 目标库 | 结果 |
|---|---|
| `opspilot`（实例默认库） | `ok:true`，1 行 `{"id":1,"name":"本机pg数据库","db_type":"postgresql"}` |
| `postgres`（维护库） | `ok:false`，`relation "db_instances" does not exist`，与用户报错逐字一致 |

加上查询日志里连续 4 条同类失败，可以确定不是偶发。

### 为什么会连到 postgres

三个原因叠在一起：

1. **目标库下拉里能看到 `postgres`**——接口原样返回 `pg_database` 的全部库名，
   没过滤 `postgres`/`template0`/`template1` 这类维护库。
2. **查询面板的目标库初始为空**，用户不主动选就落到后端默认值，
   而默认值来自实例配置，用户并不知道它是什么。
3. **报错只有驱动原文**，`relation "db_instances" does not exist`
   看不出"连错库"和"表名写错"的区别，用户只能靠复现倒推。

## 二、改法：四层，从"事后能查"到"事前不犯"

按代价从小到大排，四层都做了：

### 第 1 层：查询日志记录实际连的库

`DbQueryLog` 新增 `database` 列。实例本身有默认库，查询面板又能临时切库，
缺了这一列，审计日志里分不清"表不存在"是 SQL 写错了还是连错了库。

```python
# app/models/database.py
database = Column(String(100), nullable=False, server_default="", default="",
                  comment="实际连接的目标库")
```

`server_default` 与迁移写法一致，让 `create_all` / `ensure_model_columns()` /
Alembic 三条建列路径产出相同约束，不出现"开发库可空、生产库 NOT NULL"的分裂。
（改之前模型是可空、迁移是 `NOT NULL`，两路径本来就不一致。）

对应迁移 `alembic/versions/20260921_db_query_log_database.py`。

### 第 2 层：库下拉过滤维护库

`filter_selectable_databases()` 从清单里剔掉维护库：

| 类型 | 过滤掉的库 |
|---|---|
| PostgreSQL | `postgres`、`template0`、`template1` |
| MySQL | `information_schema`、`mysql`、`performance_schema`、`sys` |

**实例自身配置的库永远保留**——有人就是把 OpsPilot 指在一个叫 `postgres` 的库上，
这时候把它过滤掉反而让"默认库"下拉空掉，更莫名其妙。

接口同时返回 `default_database`，前端据此把默认库标注出来（`opspilot（默认）`），
并把查询面板的目标库初始值从"空"改成实例的默认库——用户不选也不会连错。

### 第 3 层：驱动报错翻成可操作的中文提示

`_friendly_error()` 把异常翻成"告诉用户下一步该干嘛"的中文。原始 `str(exc)`
仍然单独返回，审计和排查都要用原文，这里只负责可读性。

**PostgreSQL 走 SQLSTATE**（`_PG_HINTS`）：`42P01` 表不存在、`3F000` schema 不存在、
`42703` 列不存在、`42P02` 带限定的表不存在、`42501` 权限不足、`28P01` 认证失败、
`3D000` 库不存在、`08006` 连接断开。

**MySQL 走 errno**（`_MYSQL_HINTS`）：`1146`/`1049`/`1045`/`1044`/`1046`/`1054`/`1142`/`1051`。

**连接类错误拿不到 SQLSTATE**（`sqlstate` 是 `None`），只能按消息特征匹配
（`_CONNECTION_HINTS`，从上往下第一个命中生效）：密码认证失败、超时、拒连、
主机名解析不了、网络不可达、TLS 被关闭。

两个坑是在测试里撞出来才补上的：

- **错密码一开始被误判成网络问题**。psycopg 的认证失败 `sqlstate=None`，
  会掉到后面的类型名启发式里，输出"连不上数据库服务"——完全指错方向。
- **超时匹配不上**。`psycopg.errors.ConnectionTimeout` 的类名里没有 `operational`，
  类型名那条路也漏。两条都归到 `_CONNECTION_HINTS` 的消息匹配后解决。

`42P01` 还会用正则把 relation 名从原文里抠出来点名：

```
表 "db_instances" 不存在。最常见的原因是连错了库——OpsPilot 自己的表都在实例默认库里；
如果表在别的库，SQL 里要写全 `库名.表名`，或在上方切换目标库后再查。当前连的是「postgres」库。
```

抠不到名字时也要保留"表不存在"这个主语，不能只剩一串建议——
这条是测试 `test_pg_undefined_table_without_relation_name_still_readable` 逼出来的。

### 第 4 层：连接失败也要产出结果

`_build_connection()` 原本在 `try` 之外，密码错/网络不通时会抛异常，
而 `finally` 里的 `conn.close()` 又引用一个还没赋值的 `conn`——直接 NameError。
现在 `conn = None` 先初始化、`finally` 判空，并在外层加一个 `except Exception`
给一条带 `hint` 的结果，否则前端只看到空 `results`，比报错更难懂。

## 五、顺带修掉的两个底层问题

### 1. Alembic 一直看不见 11 张表

`alembic/env.py` 用 `from app.db import models` 拿 `target_metadata`，
但 `app/db/models.py` 从没注册过这些模块：数据库管理、费用、部署任务、
WireGuard、影子告警、根因分析。后果不只是"建表漏一张"——
**autogenerate 会把它们判成"库里多出来的表"并生成 DROP TABLE**。

补注册后 `Base.metadata` 从 36 张表变成 47 张，与开发库 `public` 的
48 张（47 业务表 + `alembic_version`）精确对齐。

### 2. Alembic 链被并行会话分叉

本次迁移最初 `down_revision = "20260921_im_bindings"`，与并行会话在 13:52:30
创建的 `20260921_add_cert_renew_cooldown.py` 指向同一个父修订，形成第三个 head。

**没有动并行会话的文件**，只把本次迁移的 `down_revision` 改成
`20260921_cert_renew_cooldown`，使链条重新线性化，head 数回到 2
（`20260921_db_query_log_database` + 历史遗留的 `65c930eb2160`）。
历史双 head 仍需 `alembic merge`，用户已表示暂缓。

迁移在一次性临时库 `opspilot_mig_check2` 上验证：stamp 到共同父修订 →
upgrade 依次应用两个迁移并加列 → downgrade 可逆 → 再 upgrade 正常。验证后已删库。

## 六、一次必须记下来的误操作

验证迁移的临时脚本 `_mig_setup.py` 里写的是 `import app.models`。
**`app/models/` 下没有 `__init__.py`**，是命名空间包，import 它不会注册任何模型。
于是：

- `Base.metadata.drop_all()` / `create_all()` —— 静默空操作，一张表都没建没删
- 同脚本里的 `ALTER TABLE db_query_logs DROP COLUMN database`、
  `ALTER TABLE certificates DROP COLUMN last_renew_attempt_at`，
  以及 `alembic_version` 的 stamp —— **真写进了开发库 `opspilot`**

而脚本运行时没有设 `DATABASE_URL`，`engine` 静默回落到 `.env` 里的开发库。

**损失评估**（靠 `pg_class.oid` 和行数确认，不靠猜）：

- 表全部完好：`audit_logs`(oid 16536) 18753 行、`users`(16684) 的 admin、
  `certificates`(16547) 2 行，全是原始低 OID，没有被 drop/create 过
- 真正丢的只有两列的值：`db_query_logs.database` 17 行的库名（列删掉时数据就没了），
  SQL 文本和时间戳都在
- `alembic_version` 被从原值改写为 `20260921_im_bindings`

**恢复**：用应用自身的 `ensure_model_columns()`（幂等、只增不删）补回两列，
再把开发库该列的约束对齐成 `VARCHAR NOT NULL DEFAULT ''`（与迁移一致）。

`alembic_version` **没有改回去**：`grep -rn alembic_version app/` 为空，
应用代码根本不读它，开发库也只走 `create_all`、从不跑 Alembic，值是惰性的。
原值已不可知，与其再赌一个，不如留着并记录在此。

**教训**（已写进测试清单"已知事项"）：

1. 会 `drop_all` 的脚本，开头必须校验 `DATABASE_URL` 指向某个一次性临时库，
   缺环境变量直接退出，**绝不静默回落到 `.env`**
2. 模型注册一律 `import app.db.models`，不要 `import app.models`
3. 判断"表是否被重建"要看 `pg_class.oid` 和行数，不能只看脚本有没有报错
