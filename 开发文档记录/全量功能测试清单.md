   生产部署需 `pip install -r requirements.txt`

   user_im_bindings、risk_ack_tickets/asset_host_keys/task_leases（2026-09-22 安全加固）——
   开发模式启动自动建表；生产走 Alembic `alembic upgrade head`
   （历史双 head 已由 `20260922_security_hardening_merge` 收敛为单 head）
3. **vite.config 变更**（/api 开了 ws 代理）→ **前端 dev server 必须重启一次**
4. `CONSOLE_URL` 环境变量可自定义 IM 卡片里的处理链接
5. WG 状态回读出口节点需 SSH 凭证可用；K8s Pod 日志/终端需要集群路由可达
6. **未定义名（NameError）类故障自查**：这类错误 Python 编译期不报、只有函数被调用才炸，
   测试全绿也可能带着。提交前跑一次
   `cd backend && PYTHONPATH=<pyflakes目录> .venv/Scripts/python.exe -m pyflakes app/`，
   输出里不能有 `undefined name`。注意 pyflakes 对 `from x import *` 的文件会放弃分析
   （本项目有 10 个），那部分需要额外覆盖。
7. **验证脚本不要依赖 rollback 收尾**：像 `set_issue_failed` 这类内部自带 `db.commit()` 的
   函数，跑完 rollback 是无效的，会留下真实数据。要么提前记录原值再还原，要么别连生产/开发库跑。
8. **会 drop_all 的脚本必须显式指定目标库**：2026-09-21 曾因脚本 `import app.models`
   （`app/models/` 没有 `__init__.py`，是命名空间包，import 它不注册任何模型）导致
   `drop_all`/`create_all` 静默变成空操作，而同脚本里的 `ALTER TABLE ... DROP COLUMN`
   和 `alembic stamp` 却真写进了开发库 `opspilot`——表没丢（OID 可证），但两列被删、
   `alembic_version` 被改写。恢复走应用自身的 `ensure_model_columns()`（幂等、只增不删）。
   教训：脚本开头就要校验 `DATABASE_URL` 必须指向某个一次性临时库，缺环境变量直接退出，
   **绝不静默回落到 `.env`**；模型注册一律 import `app.db.models`。
9. **开发库的 `alembic_version` 是惰性值**：开发库表结构由 lifespan `create_all` +
   `ensure_model_columns()` 维护，Alembic 迁移从不往开发库跑，应用代码也不读该表
   （`grep -rn alembic_version app/` 为空），所以它的值不影响运行。当前停在
   `20260921_im_bindings`（非 head），是上面第 8 条事故留下的，未做二次猜测改动。
