## 背景

许多操作是后端异步任务（如证书续期 `POST /api/certificates/{id}/renew`），
前端点击后立即返回，真实结果几分钟后才产生。用户可能已离开页面。
需要一个持久化的「站内信」机制，让用户下次进来仍能看到「你的 XX 操作已完成/失败」。

现有 `notifications/logs`、审计日志都是给告警系统/审计用的，不适合作为用户收件箱。
因此需要**新增一套面向登录用户的通知接口**。

## 数据模型建议

`user_notifications` 表（字段名可按后端规范调整）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string/uuid | 主键 |
| user_id | int | 接收用户 ID |
| type | string | 通知类型：`success` / `error` / `warning` / `info` |
| category | string | 业务分类：`certificate` / `vm` / `agent` / `system` 等 |
| title | string | 标题，如「证书续期完成」 |
| content | string | 详情，如「example.com 证书已续期至 2026-10-24」 |
| link | string(可空) | 点击跳转的前端路由，如 `/assets/certificates` |
| resource_id | string(可空) | 关联资源 ID，便于前端定位 |
| is_read | bool | 是否已读，默认 false |
| created_at | datetime | 创建时间 |

## 需要的接口

### 1. 获取通知列表
```
GET /api/notifications?is_read=&limit=&offset=
```
- 查询参数：`is_read`（可选，筛选未读/已读）、`limit`（默认 20）、`offset`
- 返回：
```json
{
  "items": [
    {
      "id": "xxx",
      "type": "success",
      "category": "certificate",
      "title": "证书续期完成",
      "content": "example.com 证书已续期至 2026-10-24",
      "link": "/assets/certificates",
      "resource_id": "cert_123",
      "is_read": false,
      "created_at": "2026-07-24 15:30:00"
    }
  ],
  "total": 42,
  "unread_count": 5
}
```
> `unread_count` 很关键，前端铃铛角标直接用它，避免额外请求。

### 2. 获取未读数量（轻量轮询用）
```
GET /api/notifications/unread-count
```
- 返回：`{ "unread_count": 5 }`
- 前端每 30~60 秒轮询这个接口刷新角标，比拉全量列表省流量。

### 3. 标记单条已读
```
POST /api/notifications/{id}/read
```

### 4. 全部标记已读
```
POST /api/notifications/read-all
```

### 5.（可选）删除通知
```
DELETE /api/notifications/{id}
POST   /api/notifications/clear   # 清空当前用户全部
```

## 通知的产生（后端内部）——异步任务汇聚清单

关键：**异步任务结束时（成功或失败），后端主动往 `user_notifications` 写一条记录**，
若已实现 SSE 则同时向该用户的 stream 推一帧。前端不负责写通知，只读取和标记已读。

> 设计目标：**系统所有异步任务的终态都汇聚到这个通知中心**。新增任何异步任务，
> 后端只要在任务结束时按下表 INSERT 一条即可，前端零改动自动展示。

### 统一写入规范

每条通知需填齐以下字段，前端已按这套字段渲染（图标色靠 `type`、分类标签靠 `category`、
点击跳转靠 `link`、定位资源靠 `resource_id`）：

| 字段 | 成功时 | 失败时 |
|---|---|---|
| `type` | `success` | `error`（部分成功用 `warning`） |
| `category` | 见下表 | 同左 |
| `title` | 简短结论，如「证书续期完成」 | 「证书续期失败」 |
| `content` | 带资源名+关键信息，如「example.com 已续期至 2026-10-24」 | 带失败原因，如「example.com 续期失败：DNS 校验超时」 |
| `link` | 跳到对应资源列表页 | 同左 |
| `resource_id` | 关联资源 ID（前端用于与本地即时通知去重） | 同左 |

### 各任务触发点对照表

| 触发场景 | category | type | link | 示例 content |
|---|---|---|---|---|
| 证书续期完成/失败 | `certificate` | success/error | `/assets/certificates` | example.com 已续期至 2026-10-24 / 续期失败：DNS 校验超时 |
| 证书签发完成/失败 | `certificate` | success/error | `/assets/certificates` | example.com 证书已签发 |
| 域名同步任务结束 | `domain` | success/error | `/assets/domains` | 域名同步完成，更新 5 条解析 |
| 虚机同步任务结束 | `vm` | success/error | `/assets/vms` | 虚拟机同步完成，新增 3 台 |
| 主机批量操作结束 | `host` | success/warning/error | `/assets/hosts` | 批量重启完成 8/10，2 台失败 |
| Alloy Agent 安装/卸载结束 | `agent` | success/error | `/monitoring/collector` | 主机 web-01 Agent 安装成功 |
| 数据导入/导出结束 | `system` | success/error | 对应页面 | 资产导出完成，可下载 |
| 备份/巡检定时任务 | `system` | success/warning | `/dashboard` | 每日巡检完成，3 项告警 |
| 其他长耗时任务 | 按业务补 | - | 对应页面 | - |

### 去重约定（配合 SSE）

前端点击操作后会先 `pushLocal` 一条**会话级本地占位**通知（`id` 以 `local-` 开头）做即时反馈。
当后端 SSE 推来正式记录、或下次 `fetchList` 拉到时，前端**按 `resource_id` 去重**替换掉本地占位。
因此后端写库/推送时**务必填 `resource_id`**，否则会出现一条本地 + 一条正式的重复。

## 实时推送 SSE（前端已接入，待后端实现）

> 更新（2026-07-24）：前端已经实现 SSE 客户端，连上后停止轮询、断线自动回退轮询。
> 现在需要后端提供符合以下契约的端点，联调即可秒级推送。

### 端点
```
GET /api/notifications/stream?token=<JWT>
Accept: text/event-stream
```

**鉴权方式（重要）**：原生浏览器 `EventSource` **不支持自定义请求头**，无法带
`Authorization: Bearer`。因此前端通过 **query param `token`** 传 JWT，
后端需从 query 里取 token 校验（与 header Bearer 等价）。请把 `/api/notifications/stream`
加入「允许 query token 鉴权」的白名单。

### 消息格式
每产生一条新通知，推送一帧 `data`，**内容为单条通知的完整 JSON**（字段与列表接口的
`items[]` 元素完全一致）：
```
data: {"id":"xxx","type":"success","category":"certificate","title":"证书续期完成","content":"example.com 已续期","link":"/assets/certificates","resource_id":"cert_123","is_read":false,"created_at":"2026-07-24 15:30:00"}

```
- 前端 `JSON.parse(event.data)` 后直接插入列表顶部并刷新未读角标。
- 不需要自定义 `event:` 名，用默认 `message` 事件即可（前端监听 `onmessage`）。

### 心跳（防代理断连）
建议每 15~30 秒发一帧注释行心跳（非 JSON）保活：
```
: keep-alive

```
前端对无法 `JSON.parse` 的帧会静默忽略，不影响。

### 连接与降级
- 前端挂载后立即尝试连接；`onopen` 成功即停止 `unread-count` 轮询。
- `onerror`（断线）时前端标记未连接，轮询兜底接管；`EventSource` 会自动重连。
- **仍非阻塞上线项**：没有此端点时前端自动走 45 秒轮询，功能不受影响。

### Vite 代理说明（前端本地开发）
前端 dev 用 Vite proxy 把 `/api` 转发到后端，已支持流式透传，无需后端额外配置。
生产环境若走 Nginx，需关闭对该路径的缓冲：`proxy_buffering off;` + `proxy_read_timeout` 调大。

## 前端对接方式（供后端了解链路）

1. 铃铛角标：轮询 `GET /api/notifications/unread-count`（或 SSE）
2. 点开铃铛：拉 `GET /api/notifications?limit=20`
3. 点某条通知：`POST /{id}/read` + 跳转 `link`
4. 「全部已读」按钮：`POST /read-all`

前端已预留数据结构，接口 ready 后只需把 mock 数据源换成真实 API，UI 不变。
